## Three distinct contributors

1. **Linux retains cold-open audio as a lasting backlog.** The compatibility
   graph runs while Android prepares the route. Once both ends run at the same
   average rate, the initial backlog does not disappear. Increasing its capacity
   prevents overflow but does not fix latency.
2. **The helper uses a generic, pre-route AudioTrack buffer estimate.**
   `StreamIo.prepare()` uses `max(AudioTrack.getMinBufferSize(...), 20 ms)`.
   The observed estimate is often about 320 ms. Android explicitly documents
   that this estimate does not consider the route or sink. The inspected native
   `AudioTrack::getMinFrameCount()` queries the default output rather than the
   eventual selected track's complete format/flags/route combination.
3. **The Linux graph does not advertise the downstream delay.**
   `node.latency=256/48000` requests a graph quantum; it does not describe the
   bridge queues or physical presentation delay. The current CLOCK packet uses
   playback-head position for progress/drain. That counter is not a substitute
   for AudioTrack's frame-position/presentation-time pair. In the stereo probe,
   presentation was hundreds of milliseconds behind the playback head.

Reference: [AudioTrack buffer sizing and timestamps](https://developer.android.com/reference/android/media/AudioTrack).
PipeWire documents the distinction between graph delay and stream queues in
[`pw_time`](https://docs.pipewire.org/group__pw__stream.html).

## Measured Linux queueing

An instrumented build was made on `root@192.168.104.201`, SHA256
`8d6fada035e0ef036232465fa6194c7a95a407ef4ab74ec30e86df014697d7bc`.
The same binary was tested with `LINUX_AUDIO_CLOCK_DRIVER=0` and `=1`, against
the unchanged installed helper. `LINUX_AUDIO_TIMING=1` records counters at most
once per second when transport events arrive, outside the realtime callback.

Each route played a ten-second WAV through `aplay`, selected explicitly using
`PIPEWIRE_NODE`. The table gives median frame-count differences after excluding
the first two diagnostic samples. These are software queue observations, **not
acoustic input-to-output latency or YouTube A/V measurements**.

| Route | Compatibility: produced minus accepted | Event-driven: produced minus accepted | Compatibility: produced minus playback head | Event-driven: produced minus playback head |
|---|---:|---:|---:|---:|
| Speakers | 108.67 ms | 16.00 ms | 192.67 ms | 420.23 ms |
| Headset/SCO | 347.62 ms | 16.00 ms | 427.62 ms | 340.31 ms |
| Stereo/A2DP | 683.21 ms | 16.00 ms | 733.21 ms | 151.33 ms |

All six test clients completed, but client exit alone does not prove audible
quality. The driver removed startup FIFO occupancy in these runs. It also filled
Android's existing large speaker buffer more aggressively: the speaker delay
**increased**. This is why the driver must not be promoted independently of
Android buffer policy and presentation-time reporting. Different route setup
histories also change Android's actual allocations; these are not fixed device
constants.

## Independent Android sizing probe

`AudioLatencyProbe.java` creates silence-only tracks with the helper's matching
format, attributes and performance class. It compares generic sizing, omitted
size (native minimum), and a request based on twice Android's advertised output
burst. Each test releases its track and restores communication policy. Probes
ran through root `app_process`, not the ordinary helper UID. They establish
platform behavior, not a validated replacement APK.

Median timestamp-based delay is computed as
`(written - timestamp.framePosition) / rate + timestamp.nanoTime - now`, with
unit conversion. It estimates delay at Android's reported presentation point;
it is not an acoustic measurement and depends on platform timestamp accuracy.
Initial two observations are excluded; all remaining actual routes matched.

| Route | Generic capacity | Native-minimum capacity | Generic timestamp delay | Native-minimum timestamp delay |
|---|---:|---:|---:|---:|
| Speakers, 48 kHz | 15,376 frames / 320.33 ms | 192 frames / 4 ms | 341.81 ms | 27.22 ms |
| Headset, 16 kHz | 5,152 frames / 322 ms | 644 frames / 40.25 ms | 349.53 ms | 97.37 ms |
| Stereo, 48 kHz | 15,376 frames / 320.33 ms | 3,844 frames / 80.08 ms | 617.75 ms | 497.52 ms |

The minimum speaker run had two underruns. The public output-burst property
reported 144 frames, and requesting two bursts produced a 288-frame track,
about 29 ms timestamp delay, and two underruns during measurement. It therefore
does **not** establish a universal glitch-free buffer size. On A2DP, the same
burst-request experiment was enlarged by Android to 15,376 frames again. The
generic property is not an authoritative burst size for every selected route.

## Event-driven prototype validation

The isolated production PipeWire/native fixture passes with an 80 ms bridge
queue, a deliberate 1.7-second route-opening delay, and a simulated device with
only 40 ms of write capacity. The simulated device accepts partial writes and
advances independently; its timers model hardware consumption, not production
bridge pacing. Tests cover exact sample patterns, cold-open/tail retention,
reverse-direction socket pressure, simultaneous output routing, route movement,
resource contention, capture and disconnect/reconnect.

The movement test now waits for the actual asynchronous route transition instead
of assuming `pactl move-sink-input` completion means policy has already relinked
the graph. The opt-in variable recognizes exactly `1`; `0` disables it. Failure
cleanup also destroys the endpoint's event source before freeing its context.

This does not yet validate simultaneous physical microphone capture or every
graph-driver topology on the event-driven implementation. The previous physical
capture overflow finding remains open.

## Next implementation requirements

- Keep route readiness and Android write/capture progress as pacing events.
  Do not mask startup with a larger FIFO or an arbitrary sleep.
- Bound AudioTrack's effective write-ahead after actual routing, observing
  platform-adjusted size and underrun feedback. Neither the generic minimum nor
  blindly choosing the smallest track is sufficient. Retain independent local
  and Bluetooth output-class routing and Android call priority.
- Carry valid native presentation timestamps separately from write acceptance
  and playback-head/drain progress. Preserve epoch ownership and reject stale
  timestamps after rerouting. Publish the measured downstream delay through
  PipeWire's latency interface so clients can synchronize video.
- Validate the matched helper and Linux bridge together. Include cold start,
  sustained playback, stalls, simultaneous routes, and stream movement. Re-run
  audible YouTube synchronization with the user after software timing checks.

Reduced queueing and corrected A/V synchronization are separate results. A2DP
has substantial remaining platform/transport delay in these tests; reporting it
can permit video compensation without claiming that the delay was eliminated.
